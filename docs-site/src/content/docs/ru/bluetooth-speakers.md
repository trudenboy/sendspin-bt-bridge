На этой странице собраны полевые датапоинты по Bluetooth-колонкам и наушникам, через которые прогонялся мост. Разбивка:

- **Подтверждённые** — A2DP играет чисто под обычной нагрузкой. Если для этого потребовалась конкретная версия моста, версия BlueZ или experimental-тоггл — это указано в строке.
- **С оговорками** — играет, но требуется non-default опция, апгрейд хоста или workaround.
- **Documented quirks (без подтверждённого фикса)** — стабильно ломается так, как мост не может починить сам. Перечислено, чтобы будущие читатели быстрее узнавали симптом.

Каждая строка ссылается на оригинальный issue, чтобы можно было прочитать полный диагностический тред.

:::tip[Добавьте свою колонку]
Если вашей модели в списке нет, пожалуйста, [откройте issue](https://github.com/trudenboy/sendspin-bt-bridge/issues/new) с моделью, версией BlueZ, версией моста и бандлом `Diagnostics → Download`. Датапоинты — и **положительные**, и **отрицательные** — делают этот список полезным.
:::

## Как читать эти уровни

- **Подтверждённые** ≠ "работает на любом хосте". Чистая на PulseAudio 17 + BlueZ 5.82 колонка всё ещё может потребовать тюнинг `pulse_latency_msec` на PipeWire-pulse, или замену адаптера, если onboard-контроллер перегружен. Если сомневаетесь — сверьтесь с [Bluetooth-адаптеры](/ru/bluetooth-adapters/) и [Troubleshooting](/ru/troubleshooting/).
- Записи в **С оговорками** означают, что workaround **уже доступен в мосту или в доках** — не нужно собирать кастомный firmware.
- Раздел **Documented quirks** существует, чтобы будущий оператор быстро узнавал отпечаток, а не дебажил с нуля. Если найдёте workaround — расскажите, чтобы мы переклассифицировали колонку.

## Приостановка Bluetooth-синка (suspend)

Если хост приостанавливает аудио-синк колонки в паузе между песнями, A2DP-поток колонки останавливается и запускается заново. После такого перезапуска буфер колонки может сместиться на десятки миллисекунд, и группа, которая до паузы играла синхронно, после неё может слегка разойтись.

Мост только **читает** поведение хоста и никогда не меняет настройки звука хоста. Карточка «хост приостанавливает Bluetooth-синк между песнями» появляется, когда синк ушёл в `suspended`, пока колонка была подключена, а мост этого не запрашивал, либо когда найдена политика приостановки с таймаутом короче 60 с (WirePlumber в PipeWire или `module-suspend-on-idle` в PulseAudio). Карточка исчезает после 24 часов без наблюдаемых приостановок и с чистой проверкой. Для проверки нужен `pactl`; на PipeWire ещё нужны `pw-dump` и нативный сокет PipeWire, иначе карточку вызывают только наблюдаемые приостановки.

Чтобы хост перестал приостанавливать синк, меняйте хост, а не мост:

**WirePlumber 0.5 (PipeWire 1.0 и новее)**: создайте `~/.config/wireplumber/wireplumber.conf.d/51-bluez-no-suspend.conf`:

```
monitor.bluez.rules = [
  {
    matches = [ { node.name = "~bluez_output.*" } ]
    actions = { update-props = { session.suspend-timeout-seconds = 0 } }
  }
]
```

**WirePlumber 0.4**: создайте `~/.config/wireplumber/bluetooth.lua.d/51-bluez-no-suspend.lua`:

```lua
table.insert(bluez_monitor.rules, {
  matches = { { { "node.name", "matches", "bluez_output.*" } } },
  apply_properties = { ["session.suspend-timeout-seconds"] = 0 },
})
```

Перезапустите WirePlumber (`systemctl --user restart wireplumber`) и переподключите колонку.

**PulseAudio**: выгрузите модуль в работающем сервере командой `pactl unload-module module-suspend-on-idle` и уберите строку `load-module module-suspend-on-idle` из `/etc/pulse/default.pa` (или `~/.config/pulse/default.pa`), чтобы он не загружался после перезапуска. Home Assistant OS этот модуль не загружает, там ничего делать не нужно.

## Датчик эфира (экспериментально)

Датчик эфира измеряет, когда звук каждой колонки на самом деле уходит с хоста по Bluetooth и насколько это отличается от расписания. Мост читает копию Bluetooth-трафика через HCI-монитор ядра, берёт картину громкости SBC-кадров, отправленных колонке, и сопоставляет её с картиной громкости звука, который он записал, раз в секунду по окнам в 3 секунды. В режиме `measure` воспроизведение не меняется: датчик только измеряет и показывает. В режиме `loop` он ещё и корректирует колонку (см. «Коррекция по эфиру в `loop`» ниже).

**Как включить.** **Настройки → Звук → Датчик эфира (SBC-колонки)** (`EXPERIMENTAL_AIR_SENSOR`, расширенная настройка, по умолчанию выключена). Переключатель начинает действовать после **перезапуска моста**. Для колонки датчик работает, только если:

- **Синхронизация воспроизведения** стоит в **Только измерять** (`measure`) или **Измерять и корректировать** (`loop`). При `off` панель пишет, что нужен режим measure или loop.
- Колонка играет **SBC**. Если колонка умеет и AAC, включите **Предпочитать кодек SBC**; любой другой кодек показывается как *Кодек не поддерживается*.
- Источник — 44,1 или 48 кГц, от 16 до 32 бит; иначе — *Формат не поддерживается*.
- Мост может открыть HCI-монитор ядра, а для этого нужен `CAP_NET_RAW` (только Linux). У аддона Home Assistant он уже есть. В Docker нужен `NET_RAW` в `cap_add`, как в документированном compose-файле (см. [Docker](/ru/installation/docker/)). В установках LXC и systemd мост работает от root и имеет эту возможность, если контейнер её не отбирает. Без неё панель показывает *Недоступен* с пометкой «нужен CAP_NET_RAW».

**Процессор.** На тестовой ВМ с Home Assistant OS (x86, 2 vCPU) поток моста, читающий Bluetooth-монитор, занимал 5,0–5,5 % одного ядра при двух играющих каналах (одна колонка с музыкой, одна с потоком keep-alive), то есть около **2,6 % на каждую играющую колонку**. Корреляция в собственном процессе колонки отдельно не измерялась. Если датчик всё же начнёт занимать слишком много процессорного времени, защита для каждой колонки остановит его, и панель об этом скажет. Нагрузка на Raspberry Pi пока не измерена.

**Насколько ему верить.** На тестовом стенде живые времена эфира совпали с независимым офлайн-разбором той же Bluetooth-записи в пределах 0,04 мс (p95). Эта проверка сравнивает окно с окном, поэтому смещение, общее для всего потока, она не покрывает; абсолютную сторону покрывают измерения микрофоном (см. «Калибровка» ниже).

**Панель «Синхронизация».** Когда переключатель включён, на вкладке **Синхронизация** каждой колонки появляется блок **Датчик эфира**, а на карточке устройства — метка вида `эфир: Захвачен, H -32.1 мс`.

| Строка | Что значит |
|---|---|
| **Состояние** | Одно из состояний ниже; если датчик выключен для этой колонки или недоступен, показывается причина |
| **Смещение на хосте** | `H`: насколько раньше (отрицательное) или позже расписания звук ушёл в эфир, медиана последних пяти подтверждённых окон. Оно заканчивается в эфире: собственная задержка колонки «эфир → звук» в него не входит. На тестовом стенде `H` было от −31 до −45 мс на каждый старт потока, σ ≈ 0,2 мс внутри потока (размах ≤ 0,9 мс за старт) |
| **Ошибка в эфире** | С калибровкой: опоздание колонки по звуку, `H` плюс откалиброванная задержка «эфир → звук» минус заданная для колонки задержка. Без калибровки в строке написано **Нужна калибровка** |
| **Уверенность** | От 0 до 1, из отношения пиков и доли подтверждённых окон; падает, пока датчик удерживает значение |
| **Отношение пиков (PSR)** | Насколько чётко совпало последнее подтверждённое окно; окну нужно не меньше 1,17, музыка обычно даёт от 2 до 4 |
| **Последнее подтверждение** | Сколько секунд прошло с последнего подтверждённого окна |

| Состояние | Когда |
|---|---|
| **Выключен** | Переключатель включён, но не для этой колонки (синхронизация воспроизведения не в `measure`, колонка не Bluetooth) |
| **Недоступен** | Нет HCI-монитора (нет `CAP_NET_RAW`, не Linux), монитор дал сбой или защита по процессору остановила датчик |
| **Кодек не поддерживается** / **Формат не поддерживается** | Колонка играет не SBC / формат источника не поддерживается |
| **Нет сигнала** | Звук колонке по эфиру не идёт |
| **Захват** | Звук идёт; датчик ищет первое совпадение после старта потока |
| **Захвачен** | Окно подтверждено за последние 5 с |
| **Удерживается** | Последнее подтверждённое окно было 5–20 с назад; последние значения остаются |
| **Захват потерян** | 20 с без подтверждённого окна (так бывает на длинном тихом фрагменте); значения очищены до следующего совпадения |

**Калибровка.** `H` заканчивается в эфире; время, за которое колонка проигрывает принятый звук («эфир → звук»), у каждой колонки своё. Мастер синхронизации группы измеряет его телефоном: см. [Синхронизация группы › Задержка колонки (датчик эфира)](/ru/group-sync-tuning/#задержка-колонки-датчик-эфира). Выбранный **эталон** должен играть по расписанию Sendspin: веб-плеер Sendspin на наушниках или проводном выходе либо колонка моста с синхронизацией воспроизведения в `measure` и без собственной задержки. Эталон с выключенной синхронизацией воспроизведения (старый путь вывода) или с добавленной задержкой делает значение неверным ровно на эту разницу. На тестовом стенде одна и та же колонка откалибровалась на 209 мс по эталону со старым путём и на 228,7 мс по эталону, играющему по расписанию; с 209 мс её ошибка в эфире расходилась с тем, что слышал микрофон, на 13–16 мс, с 228,7 мс — не больше чем на 3 мс.

Калибровка хранится для колонки, кодека, частоты дискретизации и Bluetooth-адаптера и показывается в разделе **Калибровки** на вкладке «Синхронизация». **Забыть** удаляет её: колонка считается неоткалиброванной для этого кодека, частоты и адаптера, пока мастер не измерит её снова.

## Коррекция по эфиру в `loop`

Когда синхронизация воспроизведения стоит в `loop` и датчик эфира включён, мост использует положение звука в эфире ещё и для коррекции колонки. Это **одна коррекция на каждый старт потока**: как только датчик захватил поток (примерно через 6–7 с после открытия выхода), мост переносит звук туда, где звук колонки должен быть, и дальше только следит за медленными изменениями. Это не постоянная погоня за измеренным значением.

Куда ставится звук, зависит от того, что мост знает о колонке:

- **Калибровка.** Мастер синхронизации группы измерил задержку колонки «эфир → звук» (см. «Калибровка» выше). Каждый старт ставится по расписанию с учётом этой задержки.
- **Изученное значение.** Калибровки нет, и мост изучает, где колонка играла в среднем в предыдущих стартах. Он учится по первым 2 стартам, дальше использует значение и сходится примерно за 6–8 стартов; первые старты идут без коррекции или поставлены лишь приблизительно. Калибровка всегда главнее изученного значения.

**Забыть** на вкладке «Синхронизация» очищает и калибровку, и изученную задержку для этого кодека, частоты и адаптера.

**Задержка по-прежнему двигает звук ровно на заданную величину.** Задержка колонки (ползунок или мастер) работает как подстройка относительно задержки, при которой сделана калибровка или изучение: изменение на 30 мс сдвигает звук на 30 мс, и коррекция его не отменяет. Смена задержки не даёт скачка значения в эфире; вместо этого панель показывает подстройку.

**На вкладке «Синхронизация»** у колонки в `loop` с датчиком есть дополнительные строки:

| Поле | Что значит |
|---|---|
| **Коррекция по эфиру** | `калибровка (N мс)`, `изучено (запусков: N)`, `нет данных (изучение: N из 2 запусков)` или `не работает: не захвачен` |
| **Смещение эфира** | Действующая сейчас коррекция, мс |
| **Коррекций по эфиру** | Сколько коррекций сделано в этом потоке |
| **Подстройка задержки** | Заданная колонке задержка относительно той, к которой относится калибровка или изучение, в виде подстройки −(D_out − D_ref), с тем же знаком, что и в журнале, и итоговой целью («цель на N мс раньше», если задержку увеличили, и «позже», если уменьшили), мс |
| **Изученные задержки** | Изученные значения по кодеку, частоте и адаптеру, у каждого — **Забыть** |

**Подсказка.** Если колонка в `loop`, но коррекции по эфиру нет, в диагностике появляется информационный пункт, а колонка работает как в `measure`. Причины: выключен переключатель датчика эфира, датчик не работает для этой колонки (не Bluetooth-колонка), датчик не может работать (см. его состояние) или он не захватил поток с момента старта.

**Требования** те же, что у датчика: переключатель **Датчик эфира (SBC-колонки)** (после изменения перезапустите мост), SBC-канал 44,1 или 48 кГц и `CAP_NET_RAW`. Если чего-то из этого нет, `loop` работает как раньше, без коррекции по эфиру.
